# Phase 0 — Browser Verification Report

Generated by the Playwright harness in this directory. Run: `npm run test:e2e` (26 tests).

Phase 0's DoD (build plan line 14):

> every screen in the prototype renders in a real Next.js app on mock data, behind
> login, visually matching the prototype — **verified in an actual browser, not by
> code inspection**.

This report records what the harness verified, what it deliberately did not, and the
judgment calls left open for human sign-off.

**Phase 0 is not declared done here.** The build plan reserves that for human sign-off.

## What the auth coverage actually proves

`e2e/auth/mintSession.ts` asks NextAuth's own `encode()` to mint the session token a real
Google login would produce, using the app's own secret from `.env.local`. The app's real
`auth()` guard then validates it normally. **Nothing about the guard is disabled or
stubbed.** Two negative tests prove the guard still bites:

- a protected route with no cookie redirects to `/login`
- a token signed with the wrong secret is rejected (so the guard validates the
  signature, not merely the cookie's presence)

### What it does NOT prove — still credentials-blocked

The build plan (line 61) anticipated this exactly:

> the full "log in with allowlisted account" browser flow can't be verified end-to-end
> until Google OAuth credentials + Supabase are wired — call this out explicitly rather
> than claiming it's done.

Both remain open:

1. **The real Google OAuth login flow is unexercised.** `GOOGLE_CLIENT_ID` is empty; the
   harness mints a token directly rather than round-tripping through Google.
2. **The fail-closed allowlist is unexercised.** The app enforces it in NextAuth's
   `signIn` callback — i.e. at login time only, not per-request. A minted session never
   passes through it, so `ALLOWED_EMAIL_DOMAIN` / `ALLOWED_EMAILS` have **zero** browser
   coverage. This is the confidentiality gate; it needs a real login to verify.

Neither can close until real Google OAuth credentials and a Supabase `DATABASE_URL` exist.

## Fidelity gaps found and fixed

All 12 captures were compared against their prototype counterpart by eye. Every gap below
was invisible to the text assertions — which is exactly why the screenshot artifacts exist.
Each now has a regression assertion.

1. **`#vijayam` detail dropped the campaigns tab bar.** `campaigns/layout.tsx` special-cased
   `pathname !== "/campaigns/vijayam"` to hide `.inner-tabs`. In the prototype `.inner-tabs`
   is a **sibling** of both `#camp-own` and `#camp-vijayam` (line 424), and `openVijayam()`
   toggles only those two divs — so the bar never disappears. Fixed; "Own Campaigns" stays
   lit on the detail route.

2. **Top Agency KPI rendered at the wrong size.** The prototype overrides that tile to
   `font-size:15px` (line 626) because an agency name is longer than a number. The port
   rendered it at the default 24px. Added a `compact` prop to `<Kpi>`; applied to that tile.

3. **Agency upload dropzone icon was left-aligned, not centred.** The markup and the
   `.upload-zone` CSS are byte-identical to the prototype — the cause is Tailwind's preflight
   setting `svg{display:block}`, which makes the icon ignore `text-align:center` and pin to
   the padding edge. The prototype has no reset, so its svg stays inline and centres. Fixed
   with `margin-inline:auto`. Asserted geometrically (icon centre ≈ zone centre) rather than
   by CSS inspection, since the CSS *looked* correct the whole time.

4. **Fan Pages tab read "All (5)" instead of "All (24)".** The port derived the label from
   `FAN_PAGES.length` (the seeded sample), so the screen contradicted its own "18/24 active
   today" KPI and the sidebar's "24" badge. 24 pages are tracked; 5 are seeded as a sample —
   the same pattern as the agency table's "Showing 10 of 500 posts". Added an explicit
   `totalTracked` to the data layer; becomes a real count when the provider goes live.

## Intentional deviation — verified as correct, do not "fix"

**Compare › Story Response Rate for Dulquer Salmaan** shows `—` in the port; the prototype
shows `1.4%`.

The port is **more correct than the prototype here**. Story Response Rate is a Graph API
insight available only for your own account — it can never be obtained for a competitor's
page. The prototype's `1.4%` is fabricated data the real app could never populate. The port
marks it `otherPrivate: true` in seed data and renders `—` (see `src/lib/data/compare.ts`).
Left as-is deliberately.

## Open question for sign-off

**Should the Campaigns sub-nav collapse on non-campaign screens?**

The port shows Own Campaigns / Hashtag Search / Agency Report in the sidebar on **every**
screen. The prototype does not, and its own signals conflict:

- `goScreen()` (Dashboard, Content, Audience, Compare, Fan Pages) **hides** `#camp-sub` — prototype line 862
- `openCampaigns()` **shows** it — line 873
- but init forces it visible with the comment *"keep subnav visible"* — line 968

So the prototype's reference shots disagree with each other: `01-dashboard.png` shows the
sub-nav (that's the init state), while `03-audience.png` and `04-compare.png` hide it. The
build plan (line 31) describes the Campaigns section as **"expandable"**, which leans toward
the accordion reading — but the port currently has no expand/collapse affordance at all.

Not changed unilaterally: this is an interaction-design decision, and the port uses real
routes where the prototype used JS toggling, so the faithful translation ("expanded when on
a `/campaigns/*` route") is a choice worth making deliberately rather than inferring.
